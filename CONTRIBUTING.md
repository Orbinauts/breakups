# Contributing

Issues and pull requests are welcome, and every pull request is reviewed. Keep a change small and focused, and check it the way CI will before you open it: `npm install`, then `npm run typecheck` and `npm test`, which need no network and no account.

A change to the ground truth is a change to its inputs, never to `data/breakups.json` by hand: edit `data/truth/hand.json` (a statement from a source, with its citation) or `data/truth/overrides.json` (a reviewer's decision, by name), run `npm run truth`, and commit the regenerated `data/breakups.json` and `docs/truth.md` with the input that changed. A new edition of a machine-read source arrives through `npm run truth:fetch`, which needs poppler's `pdftotext` only when NASA's PDF has changed and leaves a source with no new edition as it was, and the same rebuild; the weekly maintenance workflow does both by itself. The tests rebuild the truth from the committed snapshots and fail when the committed file differs. A changed truth also changes the README's counts and the scorecard it was scored against, so the simplest way to land a hand row is to push it on a branch with the rebuilt files and run `gh workflow run maintenance.yml -f from=<branch>`: the workflow folds the branch in, replays the scorecard, writes the README's tables, runs every check and merges the result.

A change to what the detector decides needs the scorecard's word for it: with the Archive beside the repository (`npm run archive:download -- <years> --warmup`, or every year), run `npm run kpi -- --all` (the years in order, each from the states the one before ended with) and commit the regenerated `kpi/latest.json` and `kpi/latest.md` with the change (the per-year files under `kpi/years/` are working files the KPI workflow keeps as artifacts, not in git), then run `npm run kpi:readme`, which writes the README's generated parts from the aggregate and the truth (the "Current results" table and the sentence saying whether the target is met, the tables of "How well it does", the truth's counts and what the quick start prints), each between its `<!-- <name>:begin -->` and `<!-- <name>:end -->` markers, and touches no prose; never edit between the markers by hand. The tests check every cell against `kpi/latest.json`, and a failing cell's diff shows the value expected; `docs/detector/events.md`, the per-event dissection, is written with the aggregate and is committed with it. The KPI workflow recomputes the aggregate from the release and refuses a change whose committed score it cannot make again. The scorecard reads every year's catalogue (each body's launch, class, decay and first publication, the plane test's orbits, the truth's parents' last sets before their events) through the catalogue index, `<archive>/index/catalogue-index.json.gz`, never from the years on disk, since the workflow holds two years at a time; it refuses to run without the index or with a stale one. Rebuild it from the whole Archive with `npm run kpi:index` (half a minute) whenever a year of the Archive is built again or added, and whenever the truth gains a row with a parent or moves one's window (the scorecard names the row it lacks), then upload it with the side files, `npm run archive:upload -- --side-only`, which refreshes the side tarball and the release's manifest without the years; `npm run archive:download` fetches it with the side files and checks that it describes the released years.

Two things make the replay quicker, and neither changes what it scores. The first read of a year's columns keeps them unpacked under `<archive>/.decoded/<year>/` (each column keyed by the year's build time and its hash in the manifest, so a year rebuilt or downloaded again is unpacked afresh), about 11 GB for the whole Archive, which saves the unpacking on every later replay (half a minute of column reads, a minute of a sequential replay's twenty-one); the folder may be deleted at any time, `BREAKUPS_DECODED=off` reads the gzipped columns and keeps nothing, and the KPI workflow, which reads each year once, sets it. To explore a change, `npm run kpi -- --all --parallel 4 --out kpi/work/<name> [--param name=value ...] [--from-states <dir>]` replays the years in four contiguous chunks of about equal sets, each in its own process, every chunk after the first starting from the states the last full sequential replay left at the year before it (under `kpi/work/states/`, or `<dir>`), then aggregates them: eleven minutes instead of twenty-one on a twelve-core machine with 36 GB. It is approximate, exact only where the change explored leaves the states at the chunks' boundaries as the run that wrote them had them, and says so on its output and in its results (`exact: false`, `statesFrom` and the chunks at the head of its `latest.json`, a note at the head of its `latest.md`); it refuses to write to `kpi/`, and the committed results and CI are always the sequential replay's, so a change found by exploring is replayed in order before it is committed. Each worker holds a year's columns, the states it reads and writes, and the catalogue, five to seven gigabytes for the recent years, so more workers than the memory holds swap: six took fourteen minutes and eight twenty-four on that machine, and the command warns when the workers asked for may not fit.

A threshold of the Confirmed channel (the confirmation rules and the attribution's) is fitted on the even years offline: replay once with the rules off into a work directory (`npm run kpi -- --all --out kpi/work/<name> --param confirmDeltaVMinMps=0 ...`, as `docs/detector/d9-confirmed.md` gives it), then `KPI_DIR=kpi/work/<name> npm run kpi:sweep -- --attributions [--set name=value] [--show]` re-applies the rules from the attribution rows and scores the Confirmed line on the training years; the replay with the values chosen is the record.

The detector `confirmed-v10` is under a prospective test ([docs/decisions/0008](docs/decisions/0008-the-detector-is-tested-prospectively-from-a-frozen-tag.md)): it is frozen at the tag `frozen-confirmed-v10` (commit `8729987`), and the scheduled workflow `.github/workflows/prospective.yml` runs `npm run prospective` from main at 02:37 UTC every day on a fresh runner. The workflow checks out main, the tag (refusing it if it no longer names `8729987`, with the detector's dependencies installed at the versions the tag's runs used) and the orphan branch `prospective`; `npm run prospective:data -- download` (`scripts/prospective/data.ts`) fetches the test's states and the current year's day slices from the release `prospective-data` and the Archive's released years before it, verifying every hash; the run pulls the year's new days (the catalogue's login from the repository's secrets `SPACETRACK_IDENTITY` and `SPACETRACK_PASSWORD`, every request in the ledger `requests.log`, which the run prints and keeps as an artifact), rebuilds the year, fetches the satellite catalogue and the space weather, annotates the year's body table, builds the frozen detector's own catalogue index over the view `<archive>/prospective/view`, replays the year in the frozen checkout from the frozen states into `<archive>/prospective/<day>/`, appends the alerts raised since the freeze to `alerts.jsonl` and a line naming the run's URL to `runs.jsonl`, and commits and pushes the branch as `github-actions[bot]`; `npm run prospective:data -- upload` then puts the day slices, and a closed year's end states and provenance once it settles, back in the release. Any error fails the run, which commits whole or not at all. `npm run prospective` still runs on a machine with the Archive beside the repository, a worktree of the tag at `../breakups-frozen` and one of the branch at `../breakups-prospective` (or the places `BREAKUPS_FROZEN` and `BREAKUPS_PROSPECTIVE` name), but never run it while the workflow is enabled: two runs would pull and log the same days. Never move the tag, push to the frozen commit, or rewrite the `prospective` branch or delete the release's assets: the commit times are the test's evidence, and the release is its memory. `npm run prospective:score` prints the Confirmed headline over the events after the freeze from the branch's log and the truth as it stands, with the lead measured from the commit that logged each alert; it is final only for the events the truth has caught up with. Pause the test with `gh workflow disable prospective.yml`, resume it with `gh workflow enable prospective.yml`, and run it at once with `gh workflow run prospective.yml`.

The project keeps itself up to date ([docs/decisions/0009](docs/decisions/0009-the-project-keeps-itself-up-to-date.md)). The scheduled workflow `.github/workflows/maintenance.yml` runs every Monday at 04:17 UTC, never at the same time as the prospective test (they share a concurrency group): it fetches GCAT's debris clouds and satellite catalogue and NASA's history (`npm run truth:fetch -- --only gcat,gcat-satcat,hoosf-16e`) and rebuilds the truth; plans the run (`npm run maintenance:plan`); where the committed aggregate no longer describes the truth or the Archive's release, downloads the whole Archive, rebuilds the index and replays every year in order; writes the README's generated parts (`npm run kpi:readme`) and the prospective score (`npm run prospective:score -- --markdown ../prospective/score.md --readme`, `score.md` on the `prospective` branch and its summary between the README's `prospective:score` markers); runs `npm run typecheck`, `npm test` and `npm run docs`; and, where anything changed, commits it as `github-actions[bot]` on a branch `maintenance/<date>`, opens a pull request whose body says what moved and why (`npm run maintenance:pr`), uploads the release's side files, squashes it into main and runs CI, the KPI workflow and the docs on main, linking their runs on the pull request. On the first run from 5 January it promotes the closed year from the prospective test's day slices into the Archive (`npm run maintenance:promote`); in the week of the first Monday of each quarter it opens the issue listing the sources to read by hand (`npm run maintenance:reminder`). A failure, or a promotion refused for GitHub's 2 GiB asset limit, opens an issue labelled `maintenance` and merges nothing. The prospective workflow opens an issue labelled `prospective-alert` for each alert it logs (`npm run maintenance:alert-issues`), once per alert key. The workflow's token may open pull requests only while the repository's Actions settings allow GitHub Actions to create them. Run it at once with `gh workflow run maintenance.yml` (`-f rescore=true` to replay the scorecard regardless, `-f merge=false` to leave the pull request open and upload nothing, `-f from=<branch>` to fold a branch in), and pause it with `gh workflow disable maintenance.yml`.
