# Contributing

Issues and pull requests are welcome, and every pull request is reviewed. Keep a change small and focused, and check it the way CI will before you open it: `npm install`, then `npm run typecheck` and `npm test`, which need no network and no account.

## The ground truth

A change to the ground truth is a change to its inputs, never to `data/breakups.json` by hand: edit `data/truth/hand.json` (a statement from a source, with its citation), `data/truth/esa-ser.json` (a new edition of ESA's table of fragmentations, typed as printed; the build places each row by its rule) or `data/truth/overrides.json` (a reviewer's decision, by name), record each quarterly news issue read in `data/truth/odqn-coverage.json`, run `npm run truth`, and commit the regenerated `data/breakups.json` and `docs/truth.md` with the input that changed. A new edition of a machine-read source arrives through `npm run truth:fetch`, which needs poppler's `pdftotext` only when NASA's PDF has changed and leaves a source with no new edition as it was, and the same rebuild; the weekly maintenance workflow does both by itself. The tests rebuild the truth from the committed snapshots and fail when the committed file differs. A changed truth also changes the counts on the ground-truth page and the scorecard it was scored against, so the simplest way to land a hand row is to push it on a branch with the rebuilt files and run `gh workflow run maintenance.yml -f from=<branch>`: the workflow folds the branch in, replays the scorecard, writes the generated tables, runs every check and merges the result.

A report of a breakup (a news article, a named analyst, an agency's notice) is the statement most often added, and it has a quicker path ([docs/decisions/0011](docs/decisions/0011-reports-reach-the-truth-through-issues-the-owner-accepts.md)). `npm run truth:add -- <statement.json>` (`scripts/truth/add.ts`) checks one statement against the hand file's schema, refuses one of a source the build reads by itself, an undated report, a report published before its event and one the file already holds, appends it after the last statement in the file's own layout and rebuilds the truth, saying which event it landed in; the hand file is never edited by hand for a report then, and a statement the build cannot take leaves it as it was. Anyone may file a report with the issue form "Report of a breakup" (`.github/ISSUE_TEMPLATE/breakup-report.yml`, labelled `breakup-report`); when the owner labels it `breakup-report-accepted`, the workflow `.github/workflows/breakup-report.yml` checks that the label was applied with admin permission (anyone else's is taken off), runs `npm run truth:add -- --form` on the issue's body, commits the statement and the rebuilt truth as the Actions bot to a branch `report/issue-<number>` and runs the maintenance workflow from it; a refused form gets a comment quoting the refusal, and can be edited and labelled again. Every maintenance run appends the statements of every waiting `report/` branch that main lacks (`npm run truth:add -- --missing-from <hand.json>`) instead of merging the branch, since two reports' branches cut from one main would not merge, and deletes the branches once main holds them. The daily watcher (`.github/workflows/watch.yml`, `npm run maintenance:watch`, `scripts/maintenance/watch.ts`; `-- --dry-run` prints what it would open and asks GitHub nothing) reads NASA's Orbital Debris Quarterly News, ESA's Space Environment Report, Jonathan's Space Report and the feeds of EarthSky, Space.com, SpaceNews and Ars Technica, and opens an issue for each new notice, never a row: a prefilled `breakup-report` issue for a report, which a person completes and the owner accepts or closes, and a `maintenance` issue for a new quarterly news issue (read it, file its breakups, record it in `data/truth/odqn-coverage.json`) or ESA edition (type its table into `data/truth/esa-ser.json`); it reads what is new against those two files. `npm run truth:add` and the form refuse a row of ESA's report, which is typed apart. A page that changed its shape fails the run with a `maintenance` issue; its reader is tested on the page as it was (`test/fixtures/watch/`), and a source is added with its reader, a fixture and a test.

## The detector and the scorecard

A change to what the detector decides needs the scorecard's word for it: with the Archive beside the repository (`npm run archive:download -- <years> --warmup`, or every year), run `npm run kpi -- --all` (the years in order, each from the states the one before ended with) and commit the regenerated `kpi/latest.json` and `kpi/latest.md` with the change (the per-year files under `kpi/years/` are working files the KPI workflow keeps as artifacts, not in git), then run `npm run kpi:readme`, which writes the generated parts of the README, `docs/results.md` and `docs/ground-truth.md` from the aggregate and the truth (the README's summary table, its sentence saying whether the target is met and what its quick start prints; the results page's tables and its sentences on the splits and the medians; the truth's counts), each between its `<!-- <name>:begin -->` and `<!-- <name>:end -->` markers, and touches no prose; never edit between the markers by hand. The tests check every cell against `kpi/latest.json`, and a failing cell's diff shows the value expected; `docs/detector/events.md`, the per-event dissection, is written with the aggregate and is committed with it. The KPI workflow recomputes the aggregate from the release and refuses a change whose committed score it cannot make again, and fails where it cannot reach the release, but on a pull request from a fork; on a pull request it runs only where the change touches a file the replay reads (a change to the docs, the tests or another workflow alone starts no run, `.github/workflows/kpi.yml` says which), and on main always. The scorecard reads every year's catalogue (each body's launch, class, decay and first publication, the plane test's orbits, the truth's parents' last sets before their events) through the catalogue index, `<archive>/index/catalogue-index.json.gz`, never from the years on disk, since the workflow holds two years at a time; it refuses to run without the index or with a stale one. Rebuild it from the whole Archive with `npm run kpi:index` (half a minute) whenever a year of the Archive is built again or added, and whenever the truth gains a row with a parent or moves one's window (the scorecard names the row it lacks), then upload it with the side files, `npm run archive:upload -- --side-only`, which refreshes the side tarball and the release's manifest without the years; `npm run archive:download` fetches it with the side files and checks that it describes the released years.

Two things make the replay quicker, and neither changes what it scores. The first read of a year's columns keeps them unpacked under `<archive>/.decoded/<year>/` (each column keyed by the year's build time and its hash in the manifest, so a year rebuilt or downloaded again is unpacked afresh), about 11 GB for the whole Archive, which saves the unpacking on every later replay (half a minute of column reads, a minute of a sequential replay's twenty-one); the folder may be deleted at any time, `BREAKUPS_DECODED=off` reads the gzipped columns and keeps nothing, and the KPI workflow, which reads each year once, sets it. To explore a change, `npm run kpi -- --all --parallel 4 --out kpi/work/<name> [--param name=value ...] [--from-states <dir>]` replays the years in four contiguous chunks of about equal sets, each in its own process, every chunk after the first starting from the states the last full sequential replay left at the year before it (under `kpi/work/states/`, or `<dir>`), then aggregates them: eleven minutes instead of twenty-one on a twelve-core machine with 36 GB. It is approximate, exact only where the change explored leaves the states at the chunks' boundaries as the run that wrote them had them, and says so on its output and in its results (`exact: false`, `statesFrom` and the chunks at the head of its `latest.json`, a note at the head of its `latest.md`); it refuses to write to `kpi/`, and the committed results and CI are always the sequential replay's, so a change found by exploring is replayed in order before it is committed. Each worker holds a year's columns, the states it reads and writes, and the catalogue, five to seven gigabytes for the recent years, so more workers than the memory holds swap: six took fourteen minutes and eight twenty-four on that machine, and the command warns when the workers asked for may not fit.

A threshold of the Confirmed channel (the confirmation rules and the attribution's) is fitted on the even years offline: replay once with the rules off into a work directory (`npm run kpi -- --all --out kpi/work/<name> --param confirmDeltaVMinMps=0 ...`, as `docs/detector/d9-confirmed.md` gives it), then `KPI_DIR=kpi/work/<name> npm run kpi:sweep -- --attributions [--set name=value] [--show]` re-applies the rules from the attribution rows and scores the Confirmed line on the training years; the replay with the values chosen is the record.

## The prospective test

The detector `confirmed-v10` is under a prospective test ([docs/decisions/0008](docs/decisions/0008-the-detector-is-tested-prospectively-from-a-frozen-tag.md)): it is frozen at the tag `frozen-confirmed-v10` (commit `8729987`), and the scheduled workflow `.github/workflows/prospective.yml` runs `npm run prospective` from main at 02:37 UTC every day on a fresh runner. The workflow checks out main, the tag (refusing it if it no longer names `8729987`, with the detector's dependencies installed at the versions the tag's runs used, the `frozenDetector` pins of `pins.json`) and the orphan branch `prospective`; `npm run prospective:data -- download` (`scripts/prospective/data.ts`) fetches the test's states and the current year's day slices from the release `prospective-data` and the Archive's released years before it, verifying every hash; the run pulls the year's new days (the catalogue's login from the repository's secrets `SPACETRACK_IDENTITY` and `SPACETRACK_PASSWORD`, every request in the ledger `requests.log`, which the run prints and keeps as an artifact), rebuilds the year, fetches the satellite catalogue and the space weather, annotates the year's body table, builds the frozen detector's own catalogue index over the view `<archive>/prospective/view`, replays the year in the frozen checkout from the frozen states into `<archive>/prospective/<day>/`, appends the alerts raised since the freeze to `alerts.jsonl` and a line naming the run's URL to `runs.jsonl`, and commits and pushes the branch as `github-actions[bot]`; `npm run prospective:data -- upload` then puts the day slices, and a closed year's end states and provenance once it settles, back in the release. Any error fails the run, which commits whole or not at all. `npm run prospective` still runs on a machine with the Archive beside the repository, a worktree of the tag at `../breakups-frozen` and one of the branch at `../breakups-prospective` (or the places `BREAKUPS_FROZEN` and `BREAKUPS_PROSPECTIVE` name), but never run it while the workflow is enabled: two runs would pull and log the same days. Never move the tag, push to the frozen commit, or rewrite the `prospective` branch or delete the release's assets: the commit times are the test's evidence, and the release is its memory. `npm run prospective:score` prints the Confirmed headline over the events after the freeze from the branch's log and the truth as it stands, with the lead measured from the commit that logged each alert; it is final only for the events the truth has caught up with. Pause the test with `gh workflow disable prospective.yml`, resume it with `gh workflow enable prospective.yml`, and run it at once with `gh workflow run prospective.yml`.

## The published breakups

The breakups fit to show are published as JSON on the repository's GitHub Pages ([docs/published.md](docs/published.md), [docs/decisions/0010](docs/decisions/0010-the-breakups-fit-to-show-are-published-as-static-json.md)). The files live under `v1/` on the orphan branch `published`, seeded once with the frozen tag's replay of 2025. After its replay, the daily prospective workflow runs `npm run published` (`scripts/published/cli.ts`) on that day's year file with main's `data/breakups.json`, over a checkout of `published`, commits `v1/` there and pushes it, then calls the Pages workflow `.github/workflows/docs.yml`, which deploys the TypeDoc reference built from main and `v1/` from `published` together; it also runs on every push to main. Never rewrite the `published` branch or commit to it by hand: its history records what was public when, and the next run merges into what it holds. A change to the rules is a change to `scripts/published/` with its tests, which include the exact lists the real 2025 and 2026 replays publish (`test/fixtures/published/`, rebuilt by `npm run published:fixtures`, `scripts/published/real-fixtures.ts`); a change to the files' shape is a change to `src/published.ts`, and one that would break a reader also raises its `PUBLISHED_VERSION`.

## Kept up to date

A weekly workflow, `.github/workflows/maintenance.yml`, keeps the project current with no one at the keyboard. Every Monday it fetches GCAT's tables and NASA's history again, rebuilds the truth, replays the scorecard over the whole Archive when the truth, the Archive or the pinned versions of the engine and the propagators changed, rewrites the generated tables of the README, the [results page](docs/results.md) and the [ground-truth page](docs/ground-truth.md), and the prospective score, and runs every check. If anything changed, it opens a pull request saying what moved and why, merges it as the Actions bot, and runs CI and the KPI workflow again on main. Each January it promotes the closed year of the prospective test into the Archive, and each quarter it opens an issue listing the sources a person must read by hand. Every run also folds in the reports the owner accepted, and a daily watcher opens an issue for each new public notice of a fragmentation it reads, for a person to complete and the owner to accept. A failure opens an issue with the log, and nothing is merged. `gh workflow disable maintenance.yml` pauses it, and [docs/decisions/0009](docs/decisions/0009-the-project-keeps-itself-up-to-date.md) says what still needs a person.

In detail: the project keeps itself up to date ([docs/decisions/0009](docs/decisions/0009-the-project-keeps-itself-up-to-date.md)). The scheduled workflow `.github/workflows/maintenance.yml` runs every Monday at 04:17 UTC, never at the same time as the prospective test (they share a concurrency group): it fetches GCAT's debris clouds and satellite catalogue and NASA's history (`npm run truth:fetch -- --only gcat,gcat-satcat,hoosf-16e`) and rebuilds the truth; plans the run (`npm run maintenance:plan`); runs `npm run typecheck` and `npm test` on that tree before any replay, so a broken build or test costs minutes rather than the replay's hour (the one test the replay makes good, that the aggregate was scored against this truth, waits for it where a replay is due); where the committed aggregate no longer describes the truth, the Archive's release or the scoring pins of `pins.json`, downloads the whole Archive, rebuilds the index and replays every year in order; writes the generated parts of the README and the documentation pages (`npm run kpi:readme`) and the prospective score (`npm run prospective:score -- --markdown ../prospective/score.md --readme`, `score.md` on the `prospective` branch and its summary between the `prospective:score` markers of `docs/results.md`); runs `npm run typecheck`, `npm test` and `npm run docs`; and, where anything changed, commits it as `github-actions[bot]` on a branch `maintenance/<date>`, opens a pull request whose body says what moved and why (`npm run maintenance:pr`), follows a main that moved during the run where the move touched nothing the run generated or was made from (no file under `data/` or `kpi/`, no generated page, no dependency manifest or pin, no file the run changed, a folded branch's included: `npm run maintenance:moved`), putting its change on the new main as one commit and running the typecheck and the tests again, and otherwise leaves the pull request unmerged for the next run; waits for CI to pass on it (GitHub holds the runs of the bot's pull request for approval, as a first-time contributor's: the run approves CI's and deletes the KPI workflow's where one started, since it runs on main after the merge), uploads the release's side files, squashes it into main and runs CI, the KPI workflow and the docs on main, linking their runs on the pull request. On the first run from 5 January it promotes the closed year from the prospective test's day slices into the Archive (`npm run maintenance:promote`); in the week of the first Monday of each quarter it opens the issue listing the sources to read by hand (`npm run maintenance:reminder`). A failure, or a promotion refused for GitHub's 2 GiB asset limit, opens an issue labelled `maintenance` and merges nothing. The prospective workflow opens an issue labelled `prospective-alert` for each alert it logs (`npm run maintenance:alert-issues`), once per alert key, and a failed run of it opens one labelled `maintenance` with the end of its log, one a failing day (`npm run maintenance:failure`). Each scheduled run of the prospective, maintenance and KPI workflows enables again any scheduled workflow GitHub disabled after sixty days without activity in the repository, never one a person disabled (`npm run maintenance:keep-alive`). The KPI workflow's Monday run comes at 12:23 UTC, after the maintenance run's longest window, in the same concurrency group. The workflow's token may open pull requests only while the repository's Actions settings allow GitHub Actions to create them. Run it at once with `gh workflow run maintenance.yml` (`-f rescore=true` to replay the scorecard regardless, `-f merge=false` to leave the pull request open and upload nothing, `-f from=<branch>` to fold a branch in), and pause it with `gh workflow disable maintenance.yml`.
